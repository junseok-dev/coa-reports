05

운영 권한 이관

회사 소유 인프라와 운영 데이터는 유지하고 저장소, 자격 증명과 관리자 권한을 새 운영 주체에 연결합니다.

적용 방식: 기존 회사 AWS의 EC2·RDS·S3, OpenAI 운영 Project, 채널톡 workspace와 서비스 도메인은 그대로 사용합니다. 회사 소유의 새 비공개 GitHub 저장소를 배포 기준으로 연결하며 데이터 복사나 새 인프라 구축은 하지 않습니다.

순서 원칙: 새 운영 담당자가 회사 계정만으로 로그인·배포·데이터 조회와 복구 확인을 끝내기 전에는 기존 저장소, OAuth client, runner, API key와 관리자 계정의 접근 권한을 제거하지 않습니다. 특히 기존 RDS를 계속 사용한다면 ENCRYPTION_KEY는 변경하지 않습니다.

실제 이관 실행 순서

앞 단계의 완료 조건을 확인한 뒤 다음 단계로 진행합니다.
순서실행 작업다음 단계 진행 조건문제 발생 시
01 사전 보존 이관 시간과 작업자를 확정하고 기능·데이터 변경을 잠시 멈춥니다. RDS 수동 복구지점, S3 versioning·백업 상태, 현재 배포 성공본과 필수 Secret 이름 목록을 기록합니다. 복구지점과 현재 정상 서비스 기준 시각을 두 명 이상이 확인합니다. 백업이나 복구 권한이 불명확하면 이관을 시작하지 않습니다.
02 회사 소유권 준비 회사 소유 비공개 저장소를 새로 만들고 기존 저장소의 전체 소스와 이력을 등록한 뒤 운영 담당자와 비상 관리자를 추가합니다. AWS·OpenAI·Google Cloud·채널톡에도 회사 계정과 MFA, 결제·보안 알림 권한을 먼저 구성합니다. 기존 담당자 도움 없이 회사 계정으로 각 콘솔과 저장소에 접속할 수 있습니다. 회사 소유자와 복구 관리자가 모두 준비될 때까지 개인 계정 권한을 유지합니다.
03 자격 증명·OAuth 준비 최소 권한의 AWS·OpenAI 운영 자격 증명을 준비하고 회사 Google Cloud Web OAuth client에 운영 도메인을 Authorized JavaScript origin으로 등록합니다. 새 최상위 관리자 회사 이메일도 확정합니다. 발급 주체, 권한 범위, 만료·회수 담당자와 OAuth origin이 문서화됩니다. 새 자격 증명은 폐기하고 기존 운영 자격 증명으로 서비스를 유지한 뒤 권한을 다시 설계합니다.
04 GitHub Secrets 등록 기존 데이터용 ENCRYPTION_KEY, DATABASE_URL, S3 버킷·prefix와 서비스 도메인은 유지합니다. 새 OAuth client·ADMIN_EMAIL과 새 운영 자격 증명을 등록합니다. JWT_SECRET은 개인 계정과 무관하므로 유지하거나, 기존 세션 종료를 감수하고 새 난수로 교체할 수 있습니다. 워크플로가 요구하는 모든 Secret 이름이 존재하고 실제 값이 소스·보고서·메신저에 남지 않습니다. 누락값을 보완하기 전에는 배포하지 않습니다. ENCRYPTION_KEY가 불확실하면 기존 데이터에 연결하지 않습니다.
05 기존 배포 연결 확인 회사 소유 EC2, 작업 폴더, chatbot.service, 도메인과 DNS는 그대로 유지합니다. 작업 폴더의 Git remote를 새 회사 저장소로 변경하고 기존 EC2의 self-hosted runner를 새 저장소에 등록합니다. 새 저장소의 runner가 online이고 main 워크플로를 받을 수 있으며 EC2·서비스·도메인 설정을 변경하지 않았습니다. 기록해 둔 기존 remote와 runner 연결로 되돌립니다. EC2 인스턴스나 도메인 설정은 변경하지 않습니다.
06 최초 배포·검증 main으로 배포한 뒤 /health, 회사 Google 로그인, 최상위 관리자 권한, 기존 대화·문서 복호화, DB 읽기·쓰기, S3 문서·FAISS, 일반·문서 질문과 상담 연결을 순서대로 확인합니다. 관리자 보안 정보에서 운영값을 확인하고 Google OAuth client ID와 최상위 관리자 이메일 인계 정보를 입력합니다. 새 운영 담당자가 회사 계정만으로 배포와 핵심 기능 검증을 직접 완료하고 결과를 기록합니다. 기존 접근 권한을 유지한 채 배포 로그와 Secret 차이를 확인하고, 필요하면 이전 정상 commit으로 복구합니다.
07 종료·회수 임시 보안 정보 보관 비밀번호를 승인된 보안 채널로 전달합니다. 새 담당자는 관리자 페이지의 관리 도구 → 보안 정보에서 이 비밀번호로 처음 잠금을 해제한 뒤 즉시 새 운영 비밀번호로 재설정합니다. 검증 완료 서명을 받은 뒤에만 기존 개인 GitHub·AWS·OpenAI·Google·채널톡 권한과 불필요한 키를 제거합니다. 회사 담당자와 비상 관리자가 독립적으로 로그인·배포·복구할 수 있고 기존 개인 권한이 남아 있지 않습니다. 독립 운영 또는 비상 복구가 확인되지 않으면 권한 회수를 중단하고 누락된 인계 항목을 보완합니다.

필수 이관 작업

영역별 작업과 완료 조건
영역작업완료 조건
GitHub 회사 소유 비공개 저장소를 새로 만들고 전체 소스·이력, 환경변수 예시와 배포 워크플로를 등록합니다. main 브랜치에 실제 비밀값 없이 전체 실행 소스가 존재합니다.
회사 계정 AWS, OpenAI와 채널톡에 운영 담당자와 비상 관리자를 등록하고 MFA·결제·보안 알림 권한을 확인합니다. 회사 계정만으로 자원 관리, 사용량 조회와 계정 복구가 가능합니다.
Google OAuth 회사 Google Cloud 프로젝트에 Web OAuth client를 만들고 운영 도메인을 Authorized JavaScript origin에 등록합니다. 회사 이메일로 관리자 로그인에 성공합니다.
GitHub Secrets 기존 회사 자원 연결값과 새 운영 자격 증명을 새 저장소에 등록합니다. 기존 RDS를 사용하므로 ENCRYPTION_KEY는 현재 운영값을 유지합니다. 실제 값이 소스·문서·메신저에 남지 않고 워크플로가 모든 필수값을 읽습니다.
배포 연결 기존 EC2·chatbot.service·도메인·DNS는 그대로 유지합니다. EC2 작업 폴더의 Git remote와 self-hosted runner만 새 회사 저장소에 연결합니다. main push로 배포되고 서비스가 정상 재시작됩니다.
운영 데이터 기존 RDS와 S3를 그대로 연결하고 이관 직전 RDS 복구지점과 S3 versioning·백업 상태를 기록합니다. 대화·문서·FAQ·프롬프트·로그와 FAISS 인덱스가 배포 전후 동일하게 조회됩니다.

  • 운영 담당자가 단독 배포와 기본 장애 확인을 완료한 뒤 기존 접근 권한 제거
