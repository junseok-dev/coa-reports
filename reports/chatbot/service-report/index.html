01

서비스 핵심

반복적인 교육 정보 상담은 승인된 지식과 AI가 처리하고, 사람의 확인이 필요한 상황은 상담 매니저에게 연결하는 서비스입니다.

교육 상담 자동화

과정 소개, 커리큘럼, 지원 대상, 일정·비용·장소, 입과 절차와 운영 규정을 자연스러운 한국어 상담 말투로 안내합니다.

승인 정보 기반 답변

관리자가 승인한 문서와 FAQ, 공식 홈페이지의 과정 정보를 우선 근거로 사용하며 확인되지 않은 구체적인 사실을 임의로 만들지 않도록 제한합니다.

사람 상담 연결

취소·환불·일정 변경, 사용자의 명시적 요청처럼 개별 확인이 필요한 상황에는 상담 매니저 연결 버튼을 제공합니다.

서비스가 의도적으로 하지 않는 것

실제 수강 등록 확정

챗봇만으로 사용자의 최종 등록·결제·수강 완료 여부를 확정하지 않습니다. 관리자 화면은 대화, 상담 요청과 링크 클릭처럼 시스템이 직접 관찰한 사실을 보여줍니다.

모든 질문을 FAQ로 고정

FAQ 일치만 반환하는 구조가 아니라 문서 검색과 대화 맥락을 활용합니다. FAQ는 반복 질문의 기준 답변이고, 상세 설명과 비교는 문서 기반 LLM 상담이 맡습니다.

운영 원칙: 관리자 화면에서 확인할 수 있는 통계, 알림, 비용과 메뉴 사용법은 화면의 안내를 기준으로 합니다. 이 보고서는 화면 사용법을 반복하기보다 서비스 구조, 데이터 책임과 환경 구성처럼 화면만으로 알기 어려운 내용을 설명합니다.

03

관리자 운영 범위

세부 사용법과 현재 수치는 관리자 화면에서 직접 확인합니다. 여기서는 운영자가 스스로 처리할 수 있는 일과 시스템 작업이 필요한 일을 구분합니다.

운영

상담 운영 대시보드, 개선 검토와 비용 관리에서 이용 흐름·미확인 문제·AWS 및 OpenAI 비용을 확인합니다.

콘텐츠

문서 검토, FAQ와 프롬프트에서 답변 근거와 상담 원칙을 변경하고 버전·승인·복구 이력을 관리합니다.

관리 도구

대화·처리·감사 로그, 데이터 콘솔, 보안 정보, 모델·암호화 설정과 관리자 권한을 목적에 맞게 사용합니다.

운영자가 관리자 화면에서 처리할 수 있는 일

  • 문서 업로드·변환 검토·승인·반려·복구와 필요한 경우 FAISS 재구성
  • FAQ 추가·수정·삭제와 프롬프트 버전 관리·복구
  • 오류·문맥 불일치·답변 불만·반복 실패·안전 처리 실패 검토와 완료 처리
  • 대화 로그 조회, 상담 세션 상세 확인, Excel 내보내기와 관리자 활동 추적
  • n·Xavis 월별 비용 파일 및 OpenAI Usage 월 비용 입력·수정·삭제
  • 허용된 운영 환경설정과 접속 정보 등록·수정·삭제, 답변·임베딩 모델 변경
  • 관리자 계정 추가·삭제와 최상위 관리자 변경

이관 후 첫 접속: 관리 도구 → 보안 정보에서 승인된 보안 채널로 전달받은 임시 보관 비밀번호를 입력해 잠금을 해제한 뒤, 즉시 비밀번호 재설정에서 새 운영 비밀번호로 변경합니다. 실제 임시 비밀번호는 공개 보고서에 기록하지 않습니다. 신규 DB는 최상위 관리자가 8자 이상이며 특수문자를 포함한 비밀번호를 최초 설정합니다.

04

배포와 환경 구성

회사 소유 AWS 인프라는 유지하고, 회사 소유의 새 비공개 저장소에 필요한 자격 증명과 설정값을 GitHub Actions Secrets로 연결합니다.

01회사 비공개 저장소 생성
02회사 자산·권한 확인
03운영 자격 증명 발급
04회사 Google OAuth 구성
05Repository Secrets 등록
06기존 배포 연결 확인
07배포·운영 검증

비밀값 관리: 저장소와 보고서에는 실제 .env, API 키, DB 비밀번호와 GitHub Secrets 값을 포함하지 않습니다. 운영값은 회사 소유 계정에서 발급해 배포 환경에 직접 등록합니다.

설정 기준: 새 저장소에서 실행하는 배포와 재배포의 기준은 GitHub Secrets입니다. 관리자 보안 정보는 운영값 확인과 인계를 돕는 화면이며, 읽기 전용 보호 키는 GitHub에서 관리하고 Google OAuth client ID와 최상위 관리자 이메일은 인계 정보로 기록합니다. 따라서 새 저장소에서는 Secrets 등록을 먼저 끝낸 뒤 배포하고, 관리자 화면에서 값이 올바르게 보이는지 확인합니다.

현재 배포에 필요한 GitHub Actions Secrets

필요성, 값을 준비하는 곳과 확인 방법
이름왜 필요한가이관 시 적용 기준등록 후 확인
OPENAI_API_KEY 질문 분류, 답변 생성과 문서 임베딩 요청을 인증합니다. 기존 회사 OpenAI 계정과 운영 Project는 유지합니다. API Platform → API keys에서 새 운영 키를 발급해 등록합니다. 일반 질문, 문서 질문과 문서 재인덱싱이 정상인지 확인합니다.
ENCRYPTION_KEY 대화·보안 정보 등 보호 필드를 Fernet 방식으로 암호화하고 복호화합니다. 기존 RDS 데이터를 유지하므로 현재 운영값을 그대로 사용합니다. 새 값으로 바꾸면 기존 암호화 데이터를 읽지 못할 수 있습니다. 대화 로그와 보안 정보 저장·재조회가 정상인지 확인하고 별도 금고에 원본을 보관합니다.
VITE_GOOGLE_CLIENT_ID 프런트 Google 로그인과 백엔드 ID token 검증이 같은 OAuth client를 사용하게 합니다. 회사 Google Cloud 프로젝트의 APIs & Services → Credentials에서 OAuth 2.0 Web client를 만들고 운영 도메인을 Authorized JavaScript origin에 등록합니다. 배포한 도메인에서 등록된 관리자 이메일로 로그인합니다.
CHANNEL_TALK_URL 사람 상담이 필요한 경우 “상담 매니저 연결하기” 버튼이 열 주소입니다. 기존 회사 채널톡 workspace와 상담 URL을 그대로 사용하고 새 저장소에 같은 값을 등록합니다. 취소·환불 또는 상담 요청 질문에서 버튼을 눌러 올바른 채널이 열리는지 확인합니다.
DATABASE_URL RDS의 대화, 지식, 설정, 로그와 관리자 데이터를 읽고 저장합니다. 기존 회사 RDS endpoint와 DB를 유지합니다. DB 자격 증명을 교체한 경우에만 새 값을 반영해 postgresql://USER:PASSWORD@HOST:5432/DB 형식으로 등록합니다. 관리자 로그인 후 조회와 저장, 시스템 상태의 DB 읽기·쓰기 검사를 확인합니다.
AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY		 백엔드가 S3 문서와 FAISS 파일을 읽고 쓰는 AWS 요청에 서명합니다. 기존 회사 AWS 계정과 자원은 유지합니다. IAM에서 필요한 S3 권한만 가진 새 운영 자격 증명을 발급하거나 EC2 IAM Role을 사용합니다. 문서 업로드·다운로드, 승인 후 인덱스 S3 동기화가 되고 다른 버킷에는 접근하지 못하는지 확인합니다.
AWS_S3_BUCKET 원본 문서, 변환 산출물, FAQ 사본과 FAISS가 저장될 버킷을 지정합니다. 기존 회사 S3 버킷과 document-chatbot 저장 구조를 그대로 사용합니다. document-chatbot prefix 아래 파일 생성과 재시작 후 인덱스 복구를 확인합니다.
JWT_SECRET Google 로그인 후 발급되는 8시간 관리자 세션 토큰에 서명합니다. 기존 값을 유지하거나 python -c "import secrets; print(secrets.token_urlsafe(48))"로 새 값을 생성합니다. 변경하면 기존 관리자 세션은 종료됩니다. 로그인과 관리자 API 호출을 확인합니다. 변경하면 기존 로그인 세션은 다시 로그인해야 합니다.
ADMIN_EMAIL DB에 관리자 목록이 없어도 최초 로그인할 수 있는 최상위 관리자 이메일입니다. Google OAuth로 로그인할 회사 소유 이메일을 정확히 등록합니다. 최초 로그인 후 관리자 화면에서 추가 관리자와 최상위 관리자 설정을 확인합니다.

이관 기준: 회사 AWS 계정의 EC2·RDS·S3, 회사 OpenAI Project와 회사 채널톡은 그대로 유지합니다. 회사 소유의 새 비공개 GitHub 저장소를 만들고 운영 자격 증명과 회사 Google OAuth client를 연결합니다. 기존 RDS를 사용하므로 ENCRYPTION_KEY는 현재 운영값을 유지합니다.

배포 작업 폴더self-hosted runner가 기존 EC2의 ~/document-chatbot_practice에서 코드를 갱신합니다.폴더와 EC2는 그대로 유지하고 Git remote를 새 회사 저장소 주소로 변경합니다.
AWS region·S3 prefix워크플로가 기본 region과 document-chatbot prefix를 기록합니다.기존 운영값과 일치하는지 확인해 그대로 유지합니다.
서비스 도메인·CORS백엔드 허용 origin과 홈페이지 링크가 소스에 포함됩니다.기존 도메인을 유지하고 회사 Google OAuth의 Authorized origin에 등록합니다.
systemd·runner워크플로는 기존 EC2의 chatbot.service와 self-hosted runner를 사용합니다.기존 EC2에서 runner를 새 회사 저장소에 등록하고 online 상태와 서비스 재시작 권한을 확인합니다.

현재 배포 동작: main에 push할 때 워크플로가 GitHub Secrets로 backend/.env를 새로 만듭니다. 따라서 재배포 후에도 유지되어야 하는 환경값의 최종 기준은 새 회사 저장소의 GitHub Secrets로 맞춰야 합니다.

운영 권한 이관

회사 소유 인프라와 운영 데이터는 유지하고 저장소, 자격 증명과 관리자 권한을 새 운영 주체에 연결합니다.

적용 방식: 기존 회사 AWS의 EC2·RDS·S3, OpenAI 운영 Project, 채널톡 workspace와 서비스 도메인은 그대로 사용합니다. 회사 소유의 새 비공개 GitHub 저장소를 배포 기준으로 연결하며 데이터 복사나 새 인프라 구축은 하지 않습니다.

순서실행 작업다음 단계 진행 조건문제 발생 시
01 사전 보존 이관 시간과 작업자를 확정하고 기능·데이터 변경을 잠시 멈춥니다. RDS 수동 복구지점, S3 versioning·백업 상태, 현재 배포 성공본과 필수 Secret 이름 목록을 기록합니다. 복구지점과 현재 정상 서비스 기준 시각을 두 명 이상이 확인합니다. 백업이나 복구 권한이 불명확하면 이관을 시작하지 않습니다.
02 회사 소유권 준비 회사 소유 비공개 저장소를 새로 만들고 기존 저장소의 전체 소스와 이력을 등록한 뒤 운영 담당자와 비상 관리자를 추가합니다. AWS·OpenAI·Google Cloud·채널톡에도 회사 계정과 MFA, 결제·보안 알림 권한을 먼저 구성합니다. 기존 담당자 도움 없이 회사 계정으로 각 콘솔과 저장소에 접속할 수 있습니다. 회사 소유자와 복구 관리자가 모두 준비될 때까지 개인 계정 권한을 유지합니다.
03 자격 증명·OAuth 준비 최소 권한의 AWS·OpenAI 운영 자격 증명을 준비하고 회사 Google Cloud Web OAuth client에 운영 도메인을 Authorized JavaScript origin으로 등록합니다. 새 최상위 관리자 회사 이메일도 확정합니다. 발급 주체, 권한 범위, 만료·회수 담당자와 OAuth origin이 문서화됩니다. 새 자격 증명은 폐기하고 기존 운영 자격 증명으로 서비스를 유지한 뒤 권한을 다시 설계합니다.
04 GitHub Secrets 등록 기존 데이터용 ENCRYPTION_KEY, DATABASE_URL, S3 버킷·prefix와 서비스 도메인은 유지합니다. 새 OAuth client·ADMIN_EMAIL과 새 운영 자격 증명을 등록합니다. JWT_SECRET은 개인 계정과 무관하므로 유지하거나, 기존 세션 종료를 감수하고 새 난수로 교체할 수 있습니다. 워크플로가 요구하는 모든 Secret 이름이 존재하고 실제 값이 소스·보고서·메신저에 남지 않습니다. 누락값을 보완하기 전에는 배포하지 않습니다. ENCRYPTION_KEY가 불확실하면 기존 데이터에 연결하지 않습니다.
05 기존 배포 연결 확인 회사 소유 EC2, 작업 폴더, chatbot.service, 도메인과 DNS는 그대로 유지합니다. 작업 폴더의 Git remote를 새 회사 저장소로 변경하고 기존 EC2의 self-hosted runner를 새 저장소에 등록합니다. 새 저장소의 runner가 online이고 main 워크플로를 받을 수 있으며 EC2·서비스·도메인 설정을 변경하지 않았습니다. 기록해 둔 기존 remote와 runner 연결로 되돌립니다. EC2 인스턴스나 도메인 설정은 변경하지 않습니다.
06 최초 배포·검증 main으로 배포한 뒤 /health, 회사 Google 로그인, 최상위 관리자 권한, 기존 대화·문서 복호화, DB 읽기·쓰기, S3 문서·FAISS, 일반·문서 질문과 상담 연결을 순서대로 확인합니다. 관리자 보안 정보에서 운영값을 확인하고 Google OAuth client ID와 최상위 관리자 이메일 인계 정보를 입력합니다. 새 운영 담당자가 회사 계정만으로 배포와 핵심 기능 검증을 직접 완료하고 결과를 기록합니다. 기존 접근 권한을 유지한 채 배포 로그와 Secret 차이를 확인하고, 필요하면 이전 정상 commit으로 복구합니다.
07 종료·회수 임시 보안 정보 보관 비밀번호를 승인된 보안 채널로 전달합니다. 새 담당자는 관리자 페이지의 관리 도구 → 보안 정보에서 이 비밀번호로 처음 잠금을 해제한 뒤 즉시 새 운영 비밀번호로 재설정합니다. 검증 완료 서명을 받은 뒤에만 기존 개인 GitHub·AWS·OpenAI·Google·채널톡 권한과 불필요한 키를 제거합니다. 회사 담당자와 비상 관리자가 독립적으로 로그인·배포·복구할 수 있고 기존 개인 권한이 남아 있지 않습니다. 독립 운영 또는 비상 복구가 확인되지 않으면 권한 회수를 중단하고 누락된 인계 항목을 보완합니다.
