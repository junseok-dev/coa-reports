05

담당자 변경과 운영 연속성

기존 개인 저장소를 넘기는 방식이 아니라, 새 담당자가 새 저장소와 자신의 운영 계정으로 다시 구성하는 절차를 기준으로 합니다.

기본 원칙: 전달 대상은 소스 코드, .env.example, 설치·검증 절차입니다. 기존 .git 이력, 실제 .env, 개인 API 키와 기존 GitHub Secrets 값은 전달하지 않습니다.

담당자 변경 전체 순서

01전달할 소스와 제외 항목 점검
02새 담당자가 새 저장소 생성
03새 계정·인프라·키 준비
04새 Secrets와 환경값 등록
05EC2·runner·도메인 연결
06최초 배포와 관리자 설정
07인수 테스트 후 기존 접근 종료
단계별 실행 내용과 완료 조건
단계기존 담당자가 준비할 것새 담당자가 수행할 것완료 조건
1. 소스 정리 main의 정상 소스, README, backend/.env.example, frontend/.env.example와 이 보고서를 준비합니다. Secret 이름만 전달합니다. 받은 파일에서 .env, .env.local, DB 파일, 로그, 캐시, 개인 인증서와 키가 없는지 확인합니다. 비밀값 검색 결과가 없고 애플리케이션 소스·마이그레이션·워크플로가 포함됩니다.
2. 새 저장소 필요한 브랜치 또는 최종 소스 버전과 변경 요약을 전달합니다. 자신의 GitHub 계정 또는 회사 조직에 새 private repository를 만들고 소스를 첫 커밋으로 올립니다. 새 저장소의 main에서 소스가 열리고 이전 개인 저장소 권한에 의존하지 않습니다.
3. 새 운영 자산 필요한 AWS 자원 종류, 외부 서비스 목록과 공개 URL 구조를 설명합니다. 개인 계정 권한은 넘기지 않습니다. 회사 소유 AWS·OpenAI·Google Cloud·LangSmith·채널톡 계정을 준비하고 EC2·RDS·S3·OAuth client를 만듭니다. 각 서비스에 새 담당자 외 비상 관리자 1명 이상이 있고 결제·MFA·알림 주체가 회사 계정입니다.
4. Secret 등록 이전 절의 Secret 이름, 목적과 발급 경로만 안내합니다. 새로 발급·생성한 값을 Repository → Settings → Secrets and variables → Actions에 같은 이름으로 등록합니다. 워크플로가 참조하는 모든 이름이 존재하며 실제 값은 문서·메신저·Git에 남지 않습니다.
5. 서버·배포 연결 필요한 Python·Node 버전, systemd 서비스와 배포 동작을 설명합니다. 새 EC2에 실행 환경·chatbot.service·self-hosted runner를 설치하고 새 저장소에 runner를 등록합니다. 작업 경로와 instance ID를 수정합니다. GitHub의 Actions → Runners에서 online이고 main push로 배포가 1회 성공합니다.
6. 최초 운영 설정 운영에 필요한 문서·FAQ·프롬프트의 범위와 정상 질문 목록을 전달합니다. 최초 Google 관리자 로그인 후 관리자 화면에서 보안 정보, 콘텐츠, 모델과 추가 관리자 계정을 설정합니다. 사용자 채팅, 관리자 로그인, 문서 검색, 상담 연결과 로그 저장이 모두 정상입니다.
7. 인수 완료 질문 대응 기간을 정하고 개인 키·기존 서버·서비스 접근을 폐기합니다. 직접 배포·콘텐츠 변경·비용 입력·장애 확인을 1회 수행하고 자산대장과 복구 자료를 보관합니다. 새 담당자가 기존 개인 계정 없이 단독 운영하고, 기존 개인 키가 모두 폐기됩니다.

데이터를 새 환경으로 가져올지 먼저 결정

권장 기본안

소스만 전달하고 새로 시작

새 DB와 S3를 사용하고 ENCRYPTION_KEY·JWT_SECRET도 새로 생성합니다. 과거 대화·로그·보안 정보는 가져오지 않으므로 개인 정보와 기존 키 의존성이 가장 적습니다.

별도 승인 필요

기존 운영 데이터도 유지

RDS snapshot 또는 승인된 내보내기와 S3 객체를 별도로 이전해야 합니다. 기존 암호화 데이터를 읽으려면 당시 ENCRYPTION_KEY도 서비스 자산으로 안전하게 옮기거나, 이전 전에 새 키로 재암호화해야 합니다.

개인 키와 데이터 암호화 키의 차이: OpenAI·AWS·LangSmith 개인 키는 제거하고 새 담당자 계정으로 재발급합니다. 반면 기존 암호화 데이터를 유지하기로 한 경우의 ENCRYPTION_KEY는 개인 서비스 키가 아니라 해당 데이터의 복호화 자산이므로, 데이터를 폐기하지 않는 한 단순 삭제하면 안 됩니다.

최종 인수 테스트

  • 새 저장소 main push로 GitHub Actions가 실행되고 새 EC2의 서비스가 재시작됩니다.
  • /health와 관리자 시스템 상태에서 API, DB 읽기·쓰기와 EC2 상태를 확인합니다.
  • Google 관리자 로그인과 추가 관리자 등록·로그인을 확인합니다.
  • FAQ 질문, 문서 기반 질문, 취소·환불 질문과 상담 연결 버튼을 각각 시험합니다.
  • 새 문서를 업로드·승인하고 FAISS와 S3 동기화 후 해당 문서 질문에 답하는지 확인합니다.
  • 대화 로그·상담 세션·처리 흐름·감사 로그와 Excel 내보내기가 정상인지 확인합니다.
  • OpenAI Usage와 LangSmith trace가 새 담당자의 Project·workspace에 기록되는지 확인합니다.
  • n·Xavis 비용 파일과 OpenAI 월 비용을 시험 입력한 뒤 수정·삭제·감사 기록을 확인합니다.
  • RDS 백업, S3 versioning 또는 백업, Secret 원본 보관 위치와 마지막 정상 commit을 기록합니다.
  • 기존 담당자의 개인 API 키, 기존 GitHub·AWS·서버 접근과 관리자 계정을 모두 제거합니다.

인수 완료 기준: 소스 파일을 받았다는 사실이 아니라 새 담당자가 자신의 계정으로 배포·로그인·문서 반영·상담 연결·로그 확인·복구 위치 확인까지 직접 마친 시점입니다.
